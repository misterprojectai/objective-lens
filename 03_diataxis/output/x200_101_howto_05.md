# How to Audit the Shell Environment Before Running Administrative Tasks

This guide shows you how to inspect and document the active shell, user identity, environment variables, and `$PATH` state before executing privileged or deployment commands, and how to detect unexpected variable overrides.

---

## Before You Begin

Ensure you have:

- A Bash shell prompt on an RHEL system — either a regular user session or an escalated session via `sudo -i` or `su -`
- Permission to read `/etc/environment`, `/etc/profile.d/`, and `~/.bashrc` if you need to trace where variables originate

---

## Steps

### 1. Confirm the active shell and shell version

Verify which shell binary is running and its version before trusting any shell-specific behaviour.

```bash
echo $SHELL
bash --version
```

Cross-check that the running process is actually Bash, not a shell substituted by a script or `su` invocation:

```bash
ps -p $$
```

---

### 2. Confirm the effective user identity

Verify who the shell believes you are — both the login identity and the effective user.

```bash
whoami
id
```

If you have escalated with `sudo -i` or `su -`, confirm the target identity carried over:

```bash
echo $USER
echo $LOGNAME
echo $HOME
```

> **Note:** `whoami` reports the effective UID. `id` reports UID, GID, and all supplementary groups — use `id` when group membership matters for the task.

---

### 3. Capture all exported environment variables

Dump the full exported environment to a baseline snapshot before making changes.

```bash
env | sort
```

To save the snapshot for comparison after the task:

```bash
env | sort > /tmp/env-before.txt
```

---

### 4. Capture all shell variables, including unexported ones

`env` shows only exported variables. Use `set` to include shell-local variables and functions that may shadow or interfere with commands.

```bash
set | sort
```

To save for later comparison:

```bash
set | sort > /tmp/set-before.txt
```

---

### 5. Inspect and validate $PATH

Display the current `$PATH` as a readable list to check for unexpected directories.

```bash
echo $PATH | tr ':' '\n'
```

On an escalated session, confirm that the path is appropriate for the privilege level — a root shell should not be inheriting a user's local `~/bin` path for privileged commands:

```bash
echo $PATH | tr ':' '\n' | grep -E '^/home|\.local'
```

If this returns any output, a user-owned directory is present in a privileged shell's `$PATH` — investigate before proceeding.

---

### 6. Detect variable overrides that shadow standard commands

Check whether any environment variables are overriding commands or altering critical behaviour.

Check for a redefined `PATH` that omits standard system directories:

```bash
echo $PATH | tr ':' '\n' | grep -c '^/usr/bin$'
```

Expected result: `1`. A result of `0` means `/usr/bin` is missing from `$PATH`.

Check for an `alias` hiding a command you are about to run:

```bash
type sudo
type useradd
type passwd
```

If any of these returns `is aliased to`, resolve the alias before proceeding:

```bash
alias
```

Check for shell functions that shadow commands:

```bash
declare -f sudo
declare -f useradd
```

Any output here means a shell function is intercepting that command name.

---

### 7. Trace the origin of a suspicious variable

If a variable holds an unexpected value, identify which startup file set it.

```bash
grep -r 'VARIABLE_NAME' /etc/profile /etc/profile.d/ ~/.bash_profile ~/.bashrc ~/.bash_login
```

Replace `VARIABLE_NAME` with the actual variable name. The file that contains the assignment is the source.

---

### 8. Compare the environment after escalation

After running `sudo -i` or `su -`, compare the current environment against the pre-escalation snapshot.

```bash
env | sort > /tmp/env-after.txt
diff /tmp/env-before.txt /tmp/env-after.txt
```

Lines beginning with `>` are variables present only in the escalated session. Lines beginning with `<` were dropped during escalation.

---

## Verification

To confirm the audit is complete and the environment is clean for privileged work:

```bash
id && echo $SHELL && echo $PATH | tr ':' '\n' | head -6 && alias | grep -E 'sudo|useradd|passwd' || echo "no critical aliases found"
```

Expected result: effective UID matches the intended account, shell is `/bin/bash`, `$PATH` shows only system directories for root sessions, and no critical command aliases are present.

## Troubleshooting

| Problem | Cause | Solution |
|---|---|---|
| `type sudo` returns `sudo is aliased to ...` | An alias was defined in `~/.bashrc` or a profile script | Run `unalias sudo` in the current session; remove the definition from its source file |
| `$PATH` contains `/home/user/.local/bin` in a root shell | `sudo -i` inherited the invoking user's environment | Use `sudo -i` (not `sudo su`) and verify `/etc/sudoers` `env_reset` is set; re-audit after a clean `sudo -i` |
| `declare -f useradd` produces output | A shell function shadows the real `useradd` binary | Unset the function with `unset -f useradd`; trace its origin with `grep -r useradd /etc/profile.d/ ~/.bashrc` |
| `diff` shows critical variable dropped after `su -` | `su -` resets the environment to the target user's defaults | Expected for `su -`; re-export any required variables explicitly after escalation |
| `/usr/bin` missing from `$PATH` | `$PATH` was overwritten without including standard directories | Restore with `export PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin` |
| `echo $USER` shows wrong identity after `sudo -i` | `sudo` preserved the invoking user's `$USER` variable | Use `id` rather than `$USER` to determine the effective identity; check `/etc/sudoers` for `env_keep` entries |
